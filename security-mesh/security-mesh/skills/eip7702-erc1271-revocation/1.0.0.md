# EIP-7702 / ERC-1271 owner-revocation hypothesis checklist

This is a falsification checklist for the reported F-001 hypothesis. It does not conclude that Finding #1736 is valid.

## Resolve source semantics first

- Confirm the exact in-scope repository and full commit.
- Locate the exact `isValidSignature` implementation and fallback path at that commit.
- Confirm the target proxy address, deployed code, implementation address, delegation design, and whether the code inspected matches the deployed target at the chosen block.
- Distinguish contract-signature validation (ERC-1271 magic-value semantics) from EOA ECDSA recovery and any EIP-7702 delegation behavior.
- Read the actual owner storage/authorization model and determine whether removal is specified to revoke this signature path. Do not infer revocation semantics solely from function names.

## Falsifiable invariant

For a validation path whose documented security model says ownership removal revokes the owner's authority, a signature relying only on that removed authority should no longer be accepted after the state transition. Confirm the intended invariant from program documentation and exact source before treating this as a requirement.

## Minimal controlled comparisons

1. Valid baseline before revocation: use a digest and signature known to be valid for the intended signer; assert the expected ERC-1271 result.
2. Same digest and same signature after revocation: change only the relevant ownership/revocation state; assert the documented expected result.
3. Alternative validation path: establish whether proxy/fallback behavior differs from the normal account path, holding other variables constant.
4. Invalid-signature control: a deliberately invalid signature must not be accepted.
5. Patched negative control: run the exact candidate assertion against an independently verified corrected implementation; the suspected acceptance must no longer occur.
6. Regression controls: preserve valid behavior for remaining authorized owners and expected contract-signature flows.

## Fork controls

- Execute only in a disposable local fork using the scope-registered nonzero block and approved RPC gateway.
- Record chain ID, fork block, code hashes, proxy/implementation mapping, compiler/tool versions, and all test assertions.
- If claiming Permit2 consequences, verify the necessary allowance/signature/deadline/token/spender prerequisites and record exact before/after balances and deltas. Never claim downstream impact based only on an ERC-1271 hypothesis.

## Falsification / inconclusive outcomes

- Reject or revise the hypothesis if the exact implementation intentionally grants EOA/delegated validation independent of the removed owner state and that behavior matches the specification.
- Mark inconclusive if source/deployed-byte correspondence, block pinning, signature comparability, or the expected revocation invariant cannot be established.
- A source-level concern or model-generated trace without an actual isolated run receipt is not a reproduced finding.
